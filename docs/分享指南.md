# Cloonex 分享与分发指南

本文档说明如何把 Cloonex 交给别人使用。按**推荐程度**排序。

## 先说结论

| 方式 | 适合场景 | 对方需要什么 | 难度 |
|---|---|---|---|
| **A. 发布到 npm**（推荐） | 公开分享给任何人 | 只要 Node.js ≥ 20.11 | 低（对方一条命令） |
| B. 发 tgz 文件 | 给几个同事试用 | Node.js + 你发的文件 | 低 |
| C. GitHub 仓库 | 想让人看到源码、提 issue | Node.js + git | 中 |
| D. 打包成独立可执行文件 | 对方不想装 Node.js | 无 | 中 |

---

## A. 发布到 npm（推荐）

### 已完成的准备工作

项目已配置好发布所需的一切，无需改动代码：

- `private` 已移除，`license` 为 MIT，`name` 为 `cloonex`（在 npmjs.org 上可用）
- `files` 只包含运行所需内容（`dist/src`、`skills`、文档、LICENSE），不含源码和测试
- `prepare` 脚本：`npm install` 和 `npm publish` 时自动编译 TypeScript，不会漏发 `dist`
- `prepublishOnly` 脚本：发布前自动跑类型检查和 34 项测试，测试不过就发不出去
- `bin` 指向 `dist/src/cli.js`，用 `npx cloonex` 即可调用

### 发布步骤

```bash
# 1. 注册 npm 账号（已有可跳过）
#    https://www.npmjs.com/signup

# 2. 登录（注意：你的 npm 目前指向公司私有源，发布必须指定公共源）
npm login --registry=https://registry.npmjs.org

# 3. 发布
npm publish --registry=https://registry.npmjs.org --access public
```

> **重要**：你的全局 registry 配置是 `https://registry.17elian.com/repository/npm-group/`（公司私有 Nexus）。
> 往这个源发布会失败或只发到内网。上面两条命令都显式指定了公共源。

### 对方如何使用

```bash
# 初始化数据目录
npx cloonex init --data-dir D:\CloonexData

# 查看要写入 Codex 的配置
npx cloonex mcp-config

# 安装开发流程技能
npx cloonex install-skill
```

把 `mcp-config` 输出的 TOML 贴进 `~/.codex/config.toml`（Windows 是 `C:\Users\<用户名>\.codex\config.toml`），然后在 Codex 里确认信任该 MCP 服务即可。

生成的配置长这样，**不含任何绝对路径**，所以在谁的机器上都能用：

```toml
[mcp_servers.cloonex]
command = 'npx'
args = ['-y', 'cloonex', 'mcp']

[mcp_servers.cloonex.env]
CLOONEX_DATA_DIR = 'D:/CloonexData'
```

### 后续更新

```bash
# 改完代码后
npm version patch     # 或 minor / major
npm publish --registry=https://registry.npmjs.org
```

对方执行 `npx -y cloonex@latest` 就会拿到新版本（`-y` 参数会自动取最新）。

## B. 直接发 tgz 文件

不用注册 npm，适合先给同事试用。

```bash
# 你这边：打包
npm pack
# 生成 cloonex-0.1.0.tgz（约 50 KB）

# 把 tgz 发给对方，对方执行：
npm install -g ./cloonex-0.1.0.tgz
cloonex init --data-dir D:\CloonexData
cloonex mcp-config
cloonex install-skill
```

对方机器上需要 Node.js ≥ 20.11。**不需要**编译工具链——SQLite 用的是纯 WASM 版本，这点已实测验证。

## C. 放到 GitHub

适合开源或让同事看源码。

```bash
git remote add origin https://github.com/<你的账号>/cloonex.git
git push -u origin main
```

对方使用：

```bash
git clone https://github.com/<你的账号>/cloonex.git
cd cloonex
npm install          # prepare 脚本会自动编译
npm run build
node dist/src/cli.js init --data-dir D:\CloonexData
node dist/src/cli.js mcp-config
node dist/src/cli.js install-skill
```

或者直接经由 git 安装：

```bash
npm install -g github:<你的账号>/cloonex
```

> 注意：`npm install -g github:...` 会执行 `prepare` 脚本编译，所以对方需要网络能访问 npm 源来装依赖。

## D. 打包成独立可执行文件（对方无需 Node.js）

如果对方完全不想装 Node.js，可以用 Node 22 的单文件可执行功能：

```bash
node --experimental-sea-config sea-config.json
# 需要额外配置，且 node-sqlite3-wasm 的 .wasm 文件需要一同分发
```

**这个方式我尚未实测**，因为 WASM 文件是运行时加载的，单文件打包需要处理资源外置问题。
如果确有需要，建议先验证可行性再采用；不要直接承诺给用户。

## 分享前必须告诉对方的事

这些是产品边界，不是免责声明，而是对方需要理解才能正确使用：

1. **数据存在本地**，默认不传给开发者，也不需要账号。但使用云端 Codex 时，被选中的项目约定、偏好和代码材料会进入模型上下文——「本地保存」和「完全离线」是两件事。
2. **SQLite 文件不等于加密**。数据受操作系统账户、磁盘权限和设备安全影响。
3. **Bug 修复任务不学习偏好**，这是设计决定，不是缺陷。
4. **理由只能来自用户表达**。模型不会替用户编造历史动机；没记录的原因会显示为「未知」。
5. **未触发过时提示 ≠ 记录一定准确**。只有关联了代码证据的说明才能在代码变化时被发现。没有证据的依赖变化无法检测。

## 维护者检查清单

发布新版本前：

```bash
npm run verify    # 类型检查 + 34 项测试
npm pack --dry-run   # 确认打包内容正确（不应包含 src/ 和 test/）
```

然后确认：

- [ ] 版本号已更新
- [ ] `npm run verify` 全部通过
- [ ] 打包内容不含源码与测试
- [ ] `mcp-config` 输出的路径无绝对路径硬编码
- [ ] README 与实际行为一致

---

## 已知未验证项（不要对外宣称已完成）

- **macOS Apple Silicon**：未在实机验证。Windows 已验证。
- **多进程并发写入**：当前为单进程单连接串行写入，未验证并发访问。
- **WAL**：WASM 版 SQLite 不支持，`journal_mode` 为 `delete`。
- **效果指标**：减少返工、降低模板感等属于待试用测量项，没有数值承诺。
