# 完整案例：找回订单导出的决定

[English](example.md) · [返回中文首页](../README.zh-CN.md)

这是一个虚构的订单导出案例，演示真实 MCP 调用，不是生产业务或模型聊天录屏。

## 直接运行

从源码安装依赖后执行：

```bash
npm run demo
```

不需要 API Key、Codex 登录、全局安装或修改 MCP 配置。脚本会创建独立的临时项目和数据库，启动真实服务；结束后关闭服务并删除本次创建的临时数据，不读取现有个人知识库。

## 演示过程

| 步骤 | 操作 | 实际核对内容 |
|---|---|---|
| 明确范围 | 注册项目、记录约定、开始任务、读取上下文 | “不请求未加载页面”进入任务上下文。 |
| 保存决定 | 记录决定，执行示例导出函数，结束任务 | 两条订单编号输出符合预期，关联文件保存了指纹。 |
| 重新连接 | 关闭第一个 MCP 服务，再启动第二个并查询 | 新进程仍能查到“仅当前页”及其理由。 |
| 修改文件 | 向关联源码追加注释，显式调用 `stale_check` | 待复核说明由 0 条变为 1 条。 |
| 检查边界 | 开始 `bugfix` 任务并尝试写偏好 | 服务端拒绝写入。 |

示例材料在 [examples/order-export](../examples/order-export)，理由来自该目录下的虚构需求文档，标记为 `external_doc`，没有冒充真实用户的表达。[文字回放](assets/demo-transcript.json)只保留经过断言的结果，去除了本机路径和任务 ID。

此次源码修改只追加注释，用于说明检测边界：指纹检查能发现文件内容变化，不能判断语义是否变化。0.2.0 的功能查询会自动核对命中说明的关联文件，`stale_check` 另提供项目范围报告。它们不会自动更新说明，也不代表代码一定有错。

## 在自己的 Codex 项目中使用

完成[安装](../README.zh-CN.md#快速开始)后，可以这样提出任务：

> 使用 Cloonex 流程开始一个新功能任务：给订单列表增加导出，仅导出当前页已加载的数据，不请求其他页、不增加服务端导出任务。先读取项目上下文；只记录有依据的理由；完成后只保存实际核对过的功能说明，并关联核对的代码文件。未经我要求，不确认长期偏好。

在后续会话中查询：

> 使用 Cloonex 查询订单导出功能，并执行过时检查。说明记录中的实现方式、已经记录的理由，以及需要结合当前代码重新核对的内容，区分历史决定与当前实现。

模型回答取决于客户端和实际指令。Cloonex 提供结构化材料，不会无感采集全部聊天，也不保证模型一定正确使用记录。

这个案例验证了跨进程持久化、理由来源、关联文件变化检测和修复任务的学习限制；没有据此宣称模型回答更好、节省 Token、兼容其他模型或业务已经验收。
